# Atlas AI: подготовка к fine-tuning

Fine-tuning Atlas строится как управляемый выпуск данных, а не как автоматическая
отправка всей истории чатов провайдеру. Экспорт подготавливает данные локально:
он ничего не загружает наружу и не запускает обучение.

## Непересекающиеся контуры обучения

Один набор данных всегда принадлежит **одному проекту** и **одному агенту**.
Например, правила, законы и отзывы Phoenix для Генерального Atlas не смешиваются
с другим игровым проектом, агентом жалоб или агентом исков.

- `--project-code` по умолчанию равен `majestic-rp`;
- `--agent-id` по умолчанию равен `atlas-tvr-a`;
- для каждого следующего проекта и агента создаётся отдельная папка и отдельный
  выпуск набора;
- один и тот же каталог нельзя случайно переиспользовать для другого проекта
  или агента;
- экспорт всех пространств остаётся возможным только по явному
  `--all-organizations`, но всё равно внутри выбранных проекта и агента.

Это важно: агент жалоб обучается только на проверенных OOC-примерах, агент исков
— на IC-материалах и стиле исков, а Генеральный Atlas получает свой собственный
набор. Общие правила и актуальные законы не «запекаются» в модель: они остаются в
RAG и обновляются независимо.

## Что попадает в кандидаты

- только ответы, которым пользователь явно поставил оценку «хороший»;
- только пара «последний вопрос пользователя → ответ Atlas»;
- без PIN, API-ключей, токенов, e-mail, IP-адресов и Discord ID;
- дубликаты удаляются;
- ответы-заглушки помечаются для особенно внимательной проверки.

Оценка «хороший» ещё не разрешает обучение. Каждый пример необходимо вручную
отметить `approved` в `review.csv`. До этого `train.jsonl` остаётся пустым.

## Сборка набора

```bash
python scripts/atlas_finetuning_dataset.py \
  --organization-id 1 \
  --project-code majestic-rp \
  --agent-id atlas-tvr-a \
  --output-dir build/atlas-finetuning
```

После проверки скопируйте `review.csv`, поставьте `approved` только качественным
примерам и повторите экспорт:

```bash
python scripts/atlas_finetuning_dataset.py \
  --organization-id 1 \
  --project-code majestic-rp \
  --agent-id atlas-tvr-a \
  --output-dir build/atlas-finetuning-reviewed \
  --approvals build/atlas-finetuning/review.csv
```

Если `--output-dir` не указан, Atlas сам создаёт изолированную папку вида
`build/atlas-finetuning/<project>/<agent>/`.

Результат содержит `train.jsonl`, `eval.jsonl` и `manifest.json`. Разделение
выполняется по целым диалогам: сообщения одного чата никогда не оказываются
одновременно в train и eval. В манифесте фиксируются контрольные суммы файлов.
В `review.csv` также есть контрольная сумма каждого примера: отметка `approved`
действительна только для той редактированной пары, которую видел проверяющий.
Если текст ответа изменился, старое одобрение не попадёт в набор автоматически.

Следующий этап — зафиксировать базовые eval-сценарии Atlas, выбрать целевую
базовую модель и лишь после ручной проверки передать версионированный набор
выбранному провайдеру. Для каждого релиза в манифесте должны быть сохранены
проект, агент, training lane, базовая модель и результаты eval.

## Как выпуск подключается после обучения

Atlas не меняет модель сразу после того, как провайдер сообщил об окончании
обучения. Сначала выпуск остаётся выключенным, проходит закрытую проверку, а
затем получает отдельную запись в `ATLAS_FINE_TUNED_ROLLOUTS_JSON` в защищённом
серверном `.env`. Запись содержит только проект, агента, имя модели, номер
выпуска и признак безопасного резерва; ключ Together хранится отдельно в
`TOGETHER_API_KEY` и никогда не попадает в JSON, логи или датасет.

```json
[
  {
    "project_code": "majestic-rp",
    "agent_id": "atlas-claims",
    "provider": "together",
    "model": "account/atlas-claims-v1",
    "release": "atlas-claims-v1",
    "enabled": true,
    "fallback": true
  }
]
```

Маршрутизатор выбирает самую точную пару `проект + агент`. Модель для жалоб
не получит корпус и стиль искового агента, а выпуск одного проекта не будет
выбран для другого. При временной ошибке провайдера Atlas один раз переключает
видимый ответ на базовую модель через OpenRouter и записывает в историю именно
фактически использованные `model`, `model_provider` и `model_release`.
Overlay и текстовый режим «Атлас 2» намеренно не используют fine-tune: первый
нуждается в низкой задержке, второй — в отдельном прямом стиле.

## Что проверяем перед настоящим обучением

Fine-tuning отвечает за манеру рассуждения, краткость, структуру и устойчивое
следование задаче. Актуальные законы по-прежнему предоставляет RAG; обучение не
используется как замена базе источников.

До выпуска новой модели сравниваются старая и новая версии на закрытом eval:

- точность номера и смысла статьи;
- отсутствие придуманных норм и ссылок;
- полнота ответа при минимально необходимом объёме;
- правильный выбор IC/OOC и пространства организации;
- отсутствие секретов и сведений из чужих частных контуров;
- задержка до первого токена и полное время ответа.

Модель не выпускается, если она улучшила стиль, но ухудшила хотя бы точность
источников или изоляцию данных. Каждый экспорт ограничен одним проектом и одним
агентом; `--all-organizations` лишь расширяет число пространств внутри этой
границы и требует явного флага.

## Закрытый eval-gate

Для каждого проекта и агента создаётся отдельный закрытый `cases.jsonl`.
В нём фиксируются вопрос, проект, сервер, фракция, агент, обязательные ссылки
или выражения, запрещённые выражения и разумный предел длины. В кейсах нельзя
указывать секреты, реальные учётные данные или личные переписки без отдельного
согласования.

Ответы базовой и кандидатной модели сохраняются отдельным разрешённым runner’ом
как `results.jsonl`, после чего проверяются локально:

```bash
python scripts/atlas_evaluation_gate.py \
  --cases private/atlas-eval/majestic-rp/atlas-claims/cases.jsonl \
  --results private/atlas-eval/majestic-rp/atlas-claims/candidate-results.jsonl \
  --output build/atlas-eval/atlas-claims-v1.json
```

Gate не делает вид, что умеет сам оценить юридический смысл. Он намеренно
останавливает выпуск при отсутствии результата, неверном проекте или агенте,
потере требуемой ссылки, нарушении длины, запрещённой фразе либо отсутствии
прозрачной записи о фактической модели. Затем человек сравнивает закрытые
отчёты базового и кандидатного выпуска и только после этого включает canary.
