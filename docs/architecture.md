# Архитектура T-Mod

T-Mod развивается как **модульный монолит**: один бот, один Docker-контейнер и одна SQLite-база,
но каждая функциональная область имеет собственные правила, сценарии, адаптеры и интерфейс.
Микросервисы для текущей нагрузки добавили бы сложность без практической пользы.

## Главный принцип зависимостей

```text
Discord UI → application service → domain
                       ↓
                repository/API port
                       ↑
             infrastructure adapter
```

* `domain` содержит модели и бизнес-правила и не импортирует Discord, SQLite, HTTP или переменные окружения;
* `application` выполняет пользовательские сценарии через объявленные порты;
* `infrastructure` реализует порты для SQLite, Discord и внешних API;
* `presentation` строит карточки, но не меняет состояние;
* `views` принимает нажатия и передаёт намерение application-сервису;
* `workers` выполняют один проверяемый шаг, а цикл запуска находится отдельно;
* `setup` регистрирует команды и обработчики в composition root.

Соседние функции не должны импортировать чужие Discord-кнопки. Навигация, технические события и
обновление операционного центра будут проходить через общие порты и события.

## Целевая структура функции

```text
modules/<feature>_domain.py
modules/<feature>_service.py
modules/<feature>_repository.py
modules/<feature>_formatting.py
modules/<feature>_embeds.py
modules/<feature>_views.py
modules/<feature>_worker.py
```

Во время перехода старый файл `<feature>.py` остаётся совместимым фасадом. Поэтому существующие
команды, постоянные `custom_id`, внешние импорты и тесты продолжают работать, пока реализация
переезжает небольшими проверяемыми частями.

## Уже выделенные границы TVRS

* `consensus_core.py` — модель, правила, переходы и снимки консенсуса;
* `consensus_service.py` — сценарии изменения состояния;
* `consensus_repository.py` — SQLite-адаптер;
* `consensus_runtime.py` — реестр активных сессий без зависимости от Discord UI;
* `delivery_outbox.py` — общая долговечная очередь с повторами, lease и fencing;
* `delivery_runtime.py` — жизненный цикл воркера и технические оповещения;
* `tvrs_delivery.py` — семантические задания и Discord-адаптеры доставки TVRS;
* `tvrs_config.py` — настройки TVRS;
* `tvrs_formatting.py` — чистое форматирование;
* `tvrs_embeds.py` — отображение сущностей Discord;
* `tvrs.py` — временный совместимый фасад, команды и ещё не перенесённая оркестрация.

Операционный центр получает краткое состояние через `consensus_runtime.py` и больше не импортирует
весь TVRS-интерфейс обратно.

Навигация между крупными функциями больше не строится на взаимных импортах Discord-классов:

* `hub_runtime.py` регистрирует экраны казны, аудита, крафтов и рынка;
* `tvrs_navigation_runtime.py` предоставляет обратный переход в TVRS;
* `operations_runtime.py` принимает сигналы обновления операционной сводки;
* `public_panel_runtime.py` подключает общую панель управления;
* `control_center_runtime.py` разрешает техническому журналу получить штатный канал;
* `craft_runtime.py` и `finance_runtime.py` связывают междоменные пользовательские сценарии без
  импорта чужих views.

Для рынка выделены `market_config.py` и чистый `market_domain.py` с идентификацией, нормализацией,
транслитерацией и ранжированием поиска. Для финансов выделены `finance_config.py` и
`finance_formatting.py`; крафт использует только эти публичные правила, а не финансовый UI.

## Долговечная доставка

Результат бизнес-операции и намерение отправить Discord-сообщение записываются в одной SQLite-
транзакции. Воркер забирает готовое задание только после commit. Поэтому сбой между записью
решения и отправкой не теряет сообщение, а сбой до commit не публикует несуществующий результат.

Очередь использует модель **at-least-once**:

* `dedupe_key` не позволяет создать второе логическое задание;
* lease с уникальным токеном и heartbeat не даёт двум воркерам штатно обрабатывать одну запись;
* fencing запрещает устаревшему воркеру изменить результат нового владельца;
* повтор выполняется с увеличивающейся задержкой;
* Discord-сообщения получают детерминированный маркер, по которому повтор находит уже принятую
  отправку после обрыва ответа;
* исчерпавшее попытки задание становится `dead`, попадает в технический журнал и может быть
  возвращено командой `/tvrs_admin target:delivery action:retry identifier:ID` только в своём
  Discord-сервере;
* пока Discord gateway отключён, задания не забираются и попытки не расходуются.

Для консенсуса атомарно выполняются: начало голосования и его приглашения; результат, статус
законопроекта и все уведомления; вето и активация повторного проекта; завершение заседания,
возврат незакрытого проекта, следующий номер пленума и финальная сводка. ID личных сообщений
сохраняется после каждого участника отдельно. Восстановление имеет собственный цикл повторов и
не зависит от появления второго события `on_ready`.

## Правила production-качества

1. Публичное поведение фиксируется contract-тестом до переноса.
2. Старый импорт сохраняется фасадом до перевода всех потребителей.
3. Один рефакторинг переносит одну ответственность и не меняет одновременно пользовательский сценарий.
4. Любая операция, которую можно повторить после сбоя, имеет ключ идемпотентности.
5. Связанные изменения состояния выполняются в одной транзакции через составные repository-операции;
   общий Unit of Work будет расширять этот механизм на остальные домены.
6. Отправка Discord-сообщений отделена от записи результата общей outbox-очередью.
7. Фоновые процессы получают `run_once()`, FakeClock и отдельные тесты без реального ожидания.
8. Ошибки пользователя не попадают в технический журнал как аварии системы.
9. Секреты не сохраняются в коде, снимках, сообщениях или тестовых фикстурах.
10. После каждого среза выполняются синтаксическая проверка, architecture tests и полный набор тестов.

GitHub Actions выполняет эти проверки на Python 3.12 при каждом push в `main`, в рабочих ветках
`codex/**` и для pull request. Workflow имеет только право чтения репозитория, отдельную временную
базу и ограничение времени выполнения.

## План разделения проекта

1. Защитные тесты, настройки и composition boundaries.
2. Полное разделение TVRS: presentation, views, lifecycle, recovery и delivery.
3. Расширение действующей transactional outbox консенсуса на рынок, финансы и крафты.
4. Market: репозиторий, синхронизация, сигналы и интерфейс; чистый поиск уже выделен.
5. Finance и Craft: отдельные домены поверх общего Unit of Work.
6. Operations и Control Center: status providers и шина событий вместо обратных импортов.
7. Activity из `main.py` в собственную функцию.
8. SGL: дела, реестры, чеки, договоры и медиа после добавления characterization-тестов.
9. Разделение `storage.py` на подключение, нумерованные миграции и репозитории; `storage.py` до конца
   перехода остаётся совместимым фасадом.

## Что нельзя делать механически

`storage.py` нельзя просто разнести по нескольким файлам: операции крафта, финансов и отмены сейчас
обновляют несколько таблиц атомарно. Сначала создаётся общий Unit of Work, затем целая транзакция
переносится без разрыва. Аналогично, Discord views TVRS переносятся только после отделения
навигации и доставки, иначе появятся новые циклические импорты.
